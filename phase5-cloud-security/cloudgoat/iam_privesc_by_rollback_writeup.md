# CloudGoat — IAM Privilege Escalation via Policy Rollback

**Platform:** CloudGoat (Rhino Security Labs)  
**Scenario:** `iam_privesc_by_rollback`  
**Environment:** AWS (Personal Account — CloudGoat Lab)  
**Date:** November 2026  
**Status:** ✅ Completed — Privilege Escalation Achieved

---

## Scenario Overview

This lab simulates a real-world AWS misconfiguration where an IAM user is granted an IAM policy that has **multiple versions**, one of which is overly permissive (admin-level). Even though the *current default* version of the policy may look restricted, AWS keeps a history of all previous policy versions. If an attacker can enumerate those versions and has permission to change the *default* version, they can roll back to an older, more permissive version — effectively escalating their own privileges without ever modifying the policy's actual permissions document.

**Attack Technique (MITRE ATT&CK):** T1548.005 — Abuse Elevation Control Mechanism (Cloud: IAM Policy Version Manipulation)

**Root Cause:** Over-permissive IAM actions (`iam:ListPolicyVersions`, `iam:SetDefaultPolicyVersion`) granted to a low-privilege user, combined with a lingering admin-level policy version never deleted.

## Step-by-Step Exploitation

### Step 1 — Enumerate Attached Policies

As the low-privilege `raynor_profile` user, the first step was identifying what IAM policies were attached:

```bash
aws iam list-attached-user-policies \
  --user-name raynor \
  --profile raynor_profile
```

**Finding:** The user had a custom-managed policy attached. Its current default version appeared restrictive on the surface.

### Step 2 — Enumerate Policy Versions

Rather than trusting the current default version, policy **version history** was checked:

```bash
aws iam list-policy-versions \
  --policy-arn <policy-arn> \
  --profile raynor_profile
```

**Finding:** Multiple policy versions existed. A prior version — **v2** — granted far broader (administrator-equivalent) permissions than the current default version. AWS does not automatically delete old policy versions, and this user had permission to change which version was active.

### Step 3 — Roll Back to the Over-Permissive Version

Using the `iam:SetDefaultPolicyVersion` permission (which should **never** be granted to non-admin users), the default version was switched back to the permissive `v2`:

```bash
aws iam set-default-policy-version \
  --policy-arn <policy-arn> \
  --version-id v2 \
  --profile raynor_profile
```

This instantly elevated the effective permissions of the `raynor` user to near-administrator level — without modifying a single permission document, only changing which existing version was "active."

### Step 4 — Verify Privilege Escalation

```bash
aws iam list-users --profile raynor_profile
```

**Result:** The command succeeded, confirming the previously low-privilege user now had administrator-level IAM read access — proving successful privilege escalation.

## Impact

In a real-world environment, this misconfiguration would allow any user with `iam:ListPolicyVersions` and `iam:SetDefaultPolicyVersion` permissions to:
- Escalate to full administrator access
- Create new IAM users/roles with unrestricted permissions
- Access, modify, or delete any resource in the AWS account
- Establish persistence by creating backdoor credentials

This is a **Critical** severity finding in any real penetration test or bug bounty cloud assessment.

---

## Remediation / Mitigation

1. **Principle of Least Privilege** — Never grant `iam:SetDefaultPolicyVersion` or `iam:CreatePolicyVersion` to non-administrative users.
2. **Delete Old Policy Versions** — Regularly audit and prune unused/over-permissive policy versions (`aws iam delete-policy-version`). AWS retains up to 5 versions by default — old permissive versions are a silent liability.
3. **IAM Access Analyzer** — Enable AWS IAM Access Analyzer to continuously flag over-permissive policies and unused permissions.
4. **SCPs (Service Control Policies)** — Use AWS Organizations SCPs to hard-block dangerous IAM actions account-wide, regardless of individual IAM policy grants.
5. **CloudTrail Monitoring** — Alert on `SetDefaultPolicyVersion` and `CreatePolicyVersion` API calls, as these are rarely used legitimately and are strong indicators of privilege escalation attempts.
